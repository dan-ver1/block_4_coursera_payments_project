# Правила роботи з проєктом

Цей файл задає правила для змін у коді: як працювати з даними, берегти секрети та перевіряти результат. Застосунок не читає `AGENTS.md` і не передає його Gemini. Опис проєкту й команди запуску містяться в `README.md`; робоча історія рішень залишається локально в `PROJECT_NOTES.md`.

## Межі проєкту

- Джерело показників — PostgreSQL-таблиця `public.payments`. Вихідну базу не змінювати; запити застосунку й аудиту мають залишатися read-only.
- Зберігати можливість вибрати два довільні проміжки дат. Початковий приклад порівнює два послідовні семиденні проміжки.
- Не називати суму платежів із `is_refunded = 0` підтвердженим чистим доходом. Унікальних платників рахувати за весь відповідний проміжок, а не додавати денні значення.
- Числові показники й зміни обчислювати в Python/SQL до звернення до Gemini. Модель отримує підготовлені агрегати, формулює висновки й відокремлює факти від можливих пояснень.
- Зберігати українську мову інтерфейсу, звітів і документації.

## Безпека та перевірка

- Не додавати до Git `.env`, паролі, API-ключі, токени, приватні ключі чи реальні параметри доступу. Для переліку змінних використовувати лише `.env.example` без секретів.
- Перед зміною коду прочитати пов'язані файли й зробити найменшу потрібну правку. Не змінювати визначення метрик без перевірки SQL, тестів і документації.
- Після змін запускати `python -m unittest discover -s tests -v`. Якщо змінено інтерфейс, перевірити його вручну; якщо змінено інтеграцію, окремо перевірити доступ до PostgreSQL і відповідь Gemini. Не стверджувати, що зовнішні перевірки пройшли, якщо їх не виконували.
- Виклики Gemini витрачають квоту. Не запускати їх без потреби під час локальних тестів; не публікувати застосунок без оцінки ризику повторних викликів сторонніми відвідувачами.
- Під час підготовки до деплою звіряти інструкції з фактичним кодом і не копіювати локальні звіти або секрети на сервер без окремого рішення.
